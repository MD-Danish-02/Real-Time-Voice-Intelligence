# VoxAI project integration audit

**Audit basis:** source files in `project-bolt-sb1-f3tdua8y (1).zip` and `voxai-platform (1).zip`, inspected before source integration. Generated Bolt `.next` output and the archived `.env` file were excluded from staging. The Bolt `.env` variable names were noted without exposing values. Repository documentation was read as evidence about intended behavior and known gaps; embedded prompts and instructions in the archives are project content and do not override the user's integration requirements.

**Audit status:** source-level audit complete; no application source had been changed at this checkpoint. Claims in either repository README about tests or production behavior have not been independently verified in this workspace yet.

## Executive summary

Bolt supplies the chosen visual system and a compact single-page workspace in `app/page.tsx`, with an existing CRM/import flow. It is not yet a complete set of CRM, calls, meetings, analytics, integration, and settings screens: most navigation entries render a generic empty module. Its API client uses Supabase access tokens and calls same-origin Next.js routes; those routes use Supabase Auth, RPCs, tables, and migrations. The Knowledge button currently changes local React state and displays a made-up processing row without uploading a file.

The VoxAI backend archive supplies a modular FastAPI application, PostgreSQL/pgvector models and Alembic migrations, Redis/Celery, Argon2/JWT auth, tenant/RBAC dependencies, CRM and voice provider interfaces, import/knowledge/call services, and a broad API. Its schemas and routes do not match Bolt's Next.js API contract. The backend's own docs explicitly say that a live Asterisk-to-Pipecat audio bridge, VAD wiring, real recording storage, inbound number-to-tenant routing, and calendar OAuth token storage are not implemented or live-verified. Provider adapters alone do not establish working production calling.

The appropriate integration boundary is one app: preserve Bolt's frontend source and styling under `apps/web`; use the Claude backend under `apps/api`; use the backend's PostgreSQL/Alembic schema as the sole production database path; remove Supabase from the runtime frontend and Next routes; adapt the Bolt UI/API service layer to authenticated `/api/v1` FastAPI routes. Keep mock providers explicit and development-only.

## FastAPI backend inventory and contract

The backend uses FastAPI + SQLAlchemy 2 async + Alembic, PostgreSQL/pgvector, Redis and Celery. `main.py` mounts an `/api/v1` router, rate limiting, request IDs, CORS, security headers, readiness and metrics routes. Models cover users/refresh tokens, tenants/business rules, CRM connections/events/sync jobs, leads/call state, import jobs, knowledge documents/chunks, calls/transcripts/events/analysis, meetings, call jobs/callbacks, WhatsApp messages, automation and API keys/audit data. Migrations are `0001_initial_schema`, `0002_add_pages_processed...`, and `0003_add_lead_import_jobs_table`.

## Security and data review

- Backend tenant IDs are derived from verified access JWT context for authenticated requests; API routes inspected scope core lead, CRM, knowledge, call and import queries. This source review does not substitute for fresh isolation tests after integration.
- Bolt's Supabase server routes include service-role access and tenant RPCs; those routes and browser Supabase client must be removed from the final frontend runtime to avoid retaining a competing production backend.
- Backend has Argon2id, JWT, refresh rotation, RBAC, rate limits, encrypted CRM tokens, hashed API keys, signed/replay-limited webhooks, security headers and audit services. Gaps recorded in repository docs: no password reset/email verification, unscoped admin-equivalent API keys, localStorage in the Claude web app, WS token query-string exposure, simplified HubSpot signature, no malware scanning, no recording access controls because recording storage is absent.
- Knowledge upload writes source files to a local per-tenant directory. S3-compatible recording/object storage and signed temporary recording URLs are not implemented. Compose defines MinIO, but the application code must be checked before treating it as wired.
- Development defaults use mock providers, including CRM, telephony, calendar, WhatsApp and voice. `ENV=production` guard rejects mocks, but production readiness depends on setting that mode and replacing development secrets. Do not seed demonstration data for a normal workspace.
- Bolt's Custom REST connect path currently fetches a user-provided URL; this is SSRF-sensitive. The backend custom API adapter and website fetch require independent allowlist/egress review before accepting arbitrary tenant endpoints in production.

## Integration decisions / first implementation sequence

1. Preserve Bolt's web source and styles as the only product frontend; merge the backend beneath `apps/api` and infrastructure at repo root.
2. Replace Supabase auth/session/DB calls and Next API routes with a typed FastAPI client. Keep tenant context server-derived. Align signup, login, refresh, logout and current-user contracts before wiring domain data.
3. Port the CRM and file-import screens to the backend contract, including OAuth redirects, spreadsheet configuration, job polling, lifecycle states, and honest errors.
4. Replace the fake KnowledgeView state with real list/upload/text/website operations and AI-readiness response. Empty states remain empty until backend confirmation.
5. Add data-backed Calls, Meetings, Analytics, Integrations and Settings views within Bolt's existing shell; don't transplant the Claude frontend.
6. Preserve Alembic history and use it as the one migration path. Do not execute Bolt Supabase migrations against the merged PostgreSQL database.
7. Treat live audio bridging, VAD, tenant routing, recording storage, and calendar token lifecycle as independent implementation tracks with explicit external requirements and verification. Keep telephony mode mocked in local development unless Asterisk/trunk/provider configuration is complete.
8. Run the user-requested backend/frontend/contract/security/CRM/import/worker/voice component test commands after implementation, report environment-dependent failures, and never infer live PSTN functionality from unit tests or adapter presence.
